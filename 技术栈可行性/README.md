## 一句话结论

**✅ 成立。** 中文语义检索全链路跑通：文本 → 向量 → 存储 → 检索，查询耗时 9 毫秒。

关键证据——**关键词搜不到的，语义能搜到**：

| 搜法 | 查询词 | 结果 |
|---|---|---|
| 关键词（传统做法） | `设备` | **命中 0 条** |
| 语义（向量检索） | `设备出故障了咋办` | **第 1 名就是「活动现场投影仪突然不亮」**，余弦相似度 0.565 |

「设备」这两个字在五条经验里**一次都没出现过**，但向量检索照样把它捞出来了。
这就是经验库非要用向量检索、而不是 `LIKE '%关键词%'` 的硬证据。

## ⚠️ 三个坑（实测踩出来的，网上抄的代码基本都带第一个）

### 坑 1：Chroma 默认不是余弦距离，`1 - distance` 是错的

这是最阴的一个——**它不报错，只是静默地给你一个错误的数字**。

Chroma 建集合时如果不指定，用的是 **L2（欧氏）空间**，而且返回的是**平方**距离。
所以满世界都能搜到的这个写法：

```python
相似度 = 1 - 距离      # ❌ 错的（在默认 L2 空间下）
```

算出来的根本不是相似度。我们第一版跑出来是 `0.130`，看着像「勉强相关」，
实际真值是 **0.565**——差了一倍多，足以让人误判「模型效果不行」。

正确写法：

```python
集合 = 客户端.create_collection(
    "experience",
    metadata={"hnsw:space": "cosine"},   # ★ 必须显式指定
)
...
相似度 = 1 - 距离      # ✅ 现在才是真的余弦相似度
```

> 原理：向量归一化后 `L2² = 2 - 2·cos`，所以 `1 - L2²/2 = cos`。
> 两条路殊途同归，但**前提是先归一化**。别赌这个前提，直接指定 cosine。

### 坑 2：别给 query 加 instruction 前缀（至少这个模型别加）

`bge` 模型主页写着「检索任务要在 query 前加一句
`为这个句子生成表示以用于检索相关文章：`」。

**实测：加了以后五条全部变差。**

| 原文 | 加前缀后 | 变化 |
|---|---|---|
| 0.5649 | 0.4919 | **−0.073** |
| 0.4299 | 0.3747 | −0.055 |
| 0.3929 | 0.3413 | −0.052 |
| 0.3543 | 0.3037 | −0.051 |
| 0.2922 | 0.2752 | −0.017 |

原因推测：那个前缀是给「短 query 检索长文档」设计的，
我们这儿 query 和文档都是短句，长度差不多，前缀反而稀释了语义。

> **结论：这个项目不加前缀，入库和查询两边都别加。**
> ⚠️ 换模型时这条要重测，别当成通用真理。

### 坑 3：集合名不能是中文

Chroma 的集合名只允许 `[a-zA-Z0-9._-]`，3–512 个字符。
写 `create_collection("经验库")` 会直接抛 `InvalidArgumentError`。

所以集合叫 `experience`，**中文放文档内容里，不要放集合名**。

## 这次验证了什么、没验证什么

诚实划一下边界，免得当成「全都搞定了」：

| ✅ 已验证 | ❌ 没验证 |
|---|---|
| 模型能下载、能加载（走 HF 镜像） | 数据量大了之后检索还快不快 |
| 文本能转成向量（512 维） | 中文分句/切分策略（长文章怎么办） |
| 能存进 Chroma、能检索 | 持久化到磁盘（现在用的是内存模式，进程一关就没了） |
| 语义检索确实能命中关键词搜不到的 | 和 MySQL 的联动（K3 经验元信息） |
| 查询耗时 9 毫秒（5 条数据） | 音频转写（faster-whisper，P1 再说） |

> **5 条数据 9 毫秒**说明不了性能，只说明链路是通的。
> 真实数据量下的表现要等有了实际数据再压测。
